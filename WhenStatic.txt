WHEN STATIC?
============

People say "static kills OOP" because a static member belongs to the
class, not to any object. OOP is about objects that keep their own data
and behaviour, and static goes around that idea:
- A static variable is like a global variable. Any code can change it,
  so a bug in one place can affect every object.
- Static methods cannot be overridden, so we lose polymorphism.
- Code that calls static methods directly is hard to test, because we
  cannot replace them with a fake version.
- If we write everything as static, we end up with procedural code
  (like C) inside Java classes.

But static is still the right choice when something belongs to the
whole concept (the class), not to one particular object. These are the
cases I think are acceptable:

1. Constants shared by all objects
   Every cart has the same maximum size, so there is no reason for each
   cart to store its own copy.
       public static final int MAX_NUMBERS_ORDERED = 20;   // Cart
       Math.PI, Integer.MAX_VALUE

2. Data that must be shared between all instances (e.g. a counter)
   In AIMS each DVD needs a unique id, so the class has to remember how
   many DVDs have been created. One DVD alone cannot know this, so
   nbDigitalVideoDiscs must be static, while id stays an instance
   variable.
       private static int nbDigitalVideoDiscs = 0;
       private int id;
       // in each constructor:
       nbDigitalVideoDiscs++;
       this.id = nbDigitalVideoDiscs;

3. Utility methods that do not use any object state
   They only work on their parameters, so creating an object just to
   call them would be pointless.
       Math.max(a, b), Math.sqrt(x), Arrays.sort(arr), Integer.parseInt("42")

4. The entry point of the program
   When the program starts there is no object yet, so main has to be
   static.
       public static void main(String[] args)

5. Factory methods (methods with a name that create objects)
   They are useful when two constructors would have the same signature.
   For example, a DVD cannot have both DigitalVideoDisc(String title)
   and DigitalVideoDisc(String category), but a static method fixes it:
       public static DigitalVideoDisc createByCategory(String category) { ... }
   Other examples: LocalDate.of(2026, 10, 18), List.of(1, 2, 3),
   Integer.valueOf(5)

6. Getting the one shared instance of a class (Singleton)
   For example one shared configuration or one database connection
   pool:
       Config.getInstance()

Conclusion
----------
Before making something static, I ask: "Does this belong to one object,
or to the class as a whole?" If it belongs to one object, like a DVD's
title or a cart's list of items, it must be an instance member. Static
is only for things that are truly common to all objects or that need no
object at all. I should be careful with static variables that can change
(case 2), because every object shares them. Static constants
(static final) are almost always safe.
